Inkling library · motion audit · decision plan

A quiet transition from grid to list.

A source-backed, implementation-free plan for making the library view change feel deliberate, fluid, and kind to the machine. The shape of the answer is simple: make the DOM contract calm before tuning the motion.

Prepared 27 Aug 2026 Scope: React + Virtuoso Masonry + Motion Research: Motion, GSAP, Anime.js Build check: passed
The short answer

Motion is ruled out for card geometry.

The library is virtualized with @virtuoso.dev/masonry, and the app uses the modern motion package through motion/react. Your hands-on result is now a hard constraint: Motion and Virtuoso do not produce a reliable card transition together in this codebase.

The grid/list transition itself is currently a custom snapshot layer: measure cards, clone visible cards, hide the live masonry, wait for a new layout, then call the browser’s Element.animate(). Motion is animating the toolbar indicator and other app surfaces, not the card geometry.

The difficult part is not “which easing?” It is that the virtualizer owns which cards exist, where their column wrappers live, and when their sizes are trustworthy.

Recommendation
Keep Motion for React-owned, non-card surfaces. Make GSAP Flip the primary card-transition spike, with Anime.js createLayout() as the lighter comparison. First solve the virtualization contract: every engine can animate mounted cards, but none can animate cards Virtuoso has removed or recycled.
What the code does now

One click crosses five moving boundaries.

01 · captureRead mounted card rectangles from the outer library wrapper.
02 · snapshotClone only cards intersecting the visible viewport.
03 · commitFlip listMode; Virtuoso changes columns and the card CSS changes shape.
04 · waitPoll rectangles every 16ms until the geometry appears stable, up to 800ms.
05 · playAnimate clone transforms for 440ms, then remove the overlay.

The production build passes. That rules out a type or bundling failure, but it does not prove a smooth interaction. The browser preview could not attach in this audit, so frame pacing and visual behavior still need to be measured in the real Tauri WebView or a browser.

Research pass

Three engines, three kinds of leverage.

The library choice matters after the DOM and virtualization contract is explicit. Every engine can animate a mounted element. None can animate a card that Virtuoso has removed from the DOM.

Non-card surfaces

Motion

Motion’s React layout system remains a good fit for the toolbar indicator, overlays, reader UI, and other elements that React can keep mounted. It is excluded from the virtualized library-card transition by the confirmed incompatibility.

  • Use layout, layout="position", and layoutDependency for stable React-owned geometry.
  • Use layoutScroll only on the actual scroll container, and layoutId selectively for deliberate one-to-one continuity.
  • AnimatePresence handles mounted/unmounted exits, but cannot preserve a node that the virtualizer removes.
  • Keep MotionConfig reducedMotion="user" aligned with the app-wide reduced-motion policy.

Layout animations · AnimatePresence · Accessibility

Primary card spike

GSAP + Flip

With Motion ruled out for card geometry, GSAP Flip is the primary specialist to test. It is strongest when the transition must coordinate an imperative before/after state, structural changes, absolute positioning, enter/leave callbacks, nested targets, interruptions, or a composed timeline.

  • Flip.getState() → commit DOM change → Flip.from(), with explicit targets and stable data-flip-id values.
  • absolute, scale, nested, prune, onEnter, onLeave, and batching are useful for a controlled snapshot layer.
  • React integration needs disciplined cleanup: useGSAP(), context scoping, and contextSafe() for click-created animations.
  • It still needs a mounted target set and explicit behavior for scroll or resize during the flip.

Flip plugin · React integration · matchMedia and reduced motion

Secondary card spike

Anime.js

Anime.js is now a serious layout candidate, not only a low-level tween engine. Its current Auto Layout API has an explicit grid/list-style toggle example and can animate grid settings, flex direction, display, DOM order, enter/exit, and shared layout IDs.

  • createLayout(root) with layout.update() is the closest direct experiment for a class-based layout switch.
  • children, enterFrom, leaveTo, swapAt, and data-layout-id provide useful control.
  • React uses createScope() plus revert(); lifecycle discipline is more imperative than Motion.
  • Its WAAPI path is attractive for transform/opacity under CPU load, but it does not remove the virtualizer’s mounted-DOM boundary.

Recommended sequence

Make the promise small enough to keep.

  1. Define the transition contract.

    Choose the honest product promise before touching an engine: the visible cards preserve their identity; cards outside the mounted window settle without ceremony; scroll is held or the transition aborts; filtering/capture updates either wait or cancel the run; reduced motion snaps geometry or uses a quiet opacity change.

    Exit: one written contract and a test matrix accepted by design and engineering.

  2. Instrument the existing experiment.

    Record view mode, actual Virtuoso scroller, mounted-card count, clone count, first/last rect mismatch, preparation duration, scrollTop/scrollHeight, React commits, long tasks, and frame times. Mark the exact moment of input, mode commit, first valid destination layout, animation start, and cleanup.

    Exit: a trace can distinguish a bad first/last state from a main-thread hitch.

  3. Repair the geometry contract before tuning.

    Use one source of truth for the requested and committed mode. Separate the virtualizer’s positioning wrapper from the visual card wrapper. Verify the actual scroll element and coordinate origin. Treat stable item IDs as identity data, not proof of DOM continuity. Decide whether contain: layout paint and whole-card nonuniform scale are acceptable for the chosen engine.

    Exit: grid and list destination boxes are correct without animation, at top/middle/bottom scroll positions and across breakpoints.

  4. Run an engine-neutral card fixture.

    Build a small, isolated fixture with about twelve mixed cards, the same card markup, the same virtualizer, and the same inner scroller. First prove the mounted-card set, item identity, coordinate origin, and destination rectangles without Motion. Then use that fixture for the GSAP Flip spike and the Anime.js Auto Layout comparison.

    Exit: no visible hold, no text stretch, no scroll jump, and a clean rapid-toggle interruption. If identity is not stable across column parents, stop tuning any animation engine and resolve the virtualization boundary.

  5. Choose the transition architecture.

    For a large library, prefer visible-window continuity and preserve virtualization. If the visual requirement is that every card travels, relax or suspend virtualization for a bounded transition or create a deliberate, non-interactive snapshot layer. Do not claim a whole-library physical transition while only a handful of cards exist.

    Exit: the architecture states exactly which cards animate, which cards settle, and what happens when the user scrolls or data changes.

  6. Validate GSAP Flip, then Anime.js.

    Motion is no longer part of the card-engine comparison. Prototype GSAP Flip first against the same fixture and measurements, with explicit target IDs and a deliberately defined mounted-window policy. Then test Anime.js createLayout as the lighter alternative if its layout controller gives the same continuity with less integration weight. Each spike should replace the transition controller, not layer another one on top of the custom overlay.

    Exit: a short decision record based on continuity, interruption, cleanup, bundle cost, and frame trace—not on a prettier isolated demo.

  7. Art-direct the quiet details last.

    Start near the design system’s 300ms layout target. Avoid a large stagger across the library; it makes a re-composition feel like a parade. Let geometry lead, let text reflow naturally, and reserve small opacity or internal transforms for entering content. Keep the toolbar indicator synchronized with the requested state. Test reduced motion as a first-class state, including preference changes while the app is open.

    Exit: the transition feels like the shelf gently changing shape, not the interface performing a trick.
Verification matrix

Small tests. Honest edges.

  • Geometry: grid → list and list → grid at top, middle, and near the end of the collection.
  • Scale: small, medium, and large data sets; mixed image ratios; notes, quotes, PDFs, videos, and X embeds.
  • Responsive: every column breakpoint, sidebar open/closed, narrow window, and scrollbar present/absent.
  • Interruption: rapid repeated toggles; scroll wheel or trackpad input during the transition; window resize during the transition.
  • Concurrent state: item capture, processing-status refresh, search/filter changes, selected inspector, and media loading during the transition.
  • Accessibility: keyboard view toggle, focus order, aria-pressed truthfulness, reduced motion, and no duplicate accessible content from snapshots.
  • Performance: a 60Hz trace with no sustained frame budget breach, no long blank hold, bounded layout reads, and cleanup of every animation and timer.
Definition of done

The transition is ready when:

  • The selected engine has one owner for geometry and one owner for lifecycle.
  • Mounted-card identity is explicit; virtualized recycling is not mistaken for continuity.
  • The actual scroll container and coordinate system are measured, not guessed.
  • The transition never waits 800ms hoping the layout becomes correct.
  • Text and artwork reflow or counter-scale without a rubber-sheet effect.
  • Offscreen behavior is intentional and documented.
  • Rapid toggles, data refresh, resize, scroll, embeds, and reduced motion have tested outcomes.
  • The frame trace supports the feeling: quiet, responsive, and unforced.
