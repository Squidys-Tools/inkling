"No code was changed. Here's the list, roughly by impact.


### The big ones

- **Glass over moving content.** The top toolbar, history/view pills, search field, and a 120px full-width bottom fade all blur what's behind them. Cards scroll directly underneath, so the blur is recomputed continuously. The top bar combines 18px blur with saturation and brightness, and the bottom fade adds two more blur layers. This is the main cost while scrolling.
- **The whole library reloads on a timer.** Every 30 seconds — and again after background-job updates settle (400ms trailing pause) — the app re-fetches every item and every item's job status, rebuilds every card object, and re-renders the visible grid. On a large library that's a lot of repeated work for a handful of changed items.
- **File capture handles the entire file up front.** Picking or dropping a file reads it completely into the UI, expands it into an array of individual numbers, sends that across, then writes it and, for images, builds the thumbnail before the card appears. Large images, PDFs, or videos can freeze capture and use many times the file size in memory.

### While browsing

- **Opening an item animates its position and size.** The overlay and everything inside it — image, inspector, toolbar — recalculates layout on every frame of the open/close flight. Animating a scaled/translated snapshot would be much cheaper.
- **Switching grid/list clones every visible card.** Each clone includes its image, and each clone is measured repeatedly. On a large window this is a visible hitch.
- **Opening or closing the sidebar animates width and padding,** so the whole grid reflows for the full 300ms.
- **Panning a zoomed image re-renders the viewer on every pointer move** instead of just moving the image.
- **Every new search result remounts the entire masonry grid.** That recreates all visible cards and images and resets video/embed state. The reset is intentional, but the cost is paid on every result change.

### Search and data

- **Semantic search reads and compares every stored embedding in one pass,** on the same part of the app that serves files and handles storage. As the library grows, search and the Similar tab get slower and can hold up other work.
- **Every refresh asks for job statuses for every item in one query.** Large libraries create a very large query and can hit the database's limit; only active/failed jobs or changes since the last refresh are needed.
- **The Archive tab loads, converts, and draws every archived item at once,** and requests job summaries for all of them. A few hundred archived items means a lot of cards and images at once.

### Files, media, and settings

- **The local asset handler reads each requested file fully into memory,** with no cache headers and no range support. Large images/PDFs and video seeking can re-read whole files, and repeated grid mounts can do it again.
- **Locally saved video cards load the real video file just to show a frame.** A poster or thumbnail until play would avoid reading the file while scrolling.
- **Opening Settings walks every asset file one at a time** to compute library size, every time. The backend has a cache, but the UI always asks for a fresh scan.

### Background

- **The mascot redraws a detailed SVG through React on every animation frame, in two places, all the time,** even when idle or the sidebar is collapsed. It's intentional, but it's why the app never truly idles. Pausing when not visible, or drawing directly instead of through React, would remove the constant cost.

If you only take three: incremental library refresh, lighter/targeted glass blur over the grid, and a streaming file handoff."
