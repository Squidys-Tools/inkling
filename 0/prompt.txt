# Second opinion: embedding decode in `electron/storage/search.ts`

**Recommendation in one sentence:** take the `Float32Array` view fix — it's the smallest possible change, produces bit-for-bit identical scores, is ~35× faster than the current decode under V8, and it already lands you at the performance floor that a decoded-vector cache would reach, so skip the cache entirely.

## Measured results

Benchmarked in my temp dir (`C:\Users\chris\AppData\Local\Temp\inkling-embed-bench.mjs`, `-fine.mjs`), 2,000 random 768-dim blobs, `process.cpuUsage()` deltas, min/median/max over 9 runs with each sample spanning 5 full scans (Windows quantizes CPU usage to ~15.6ms, so short loops need aggregation). Primary numbers under **Node 26 / V8** (the engine family Electron 45 ships; Bun/JSC included as a second data point):

| Option | CPU ms / 1,000 vectors (V8) | Scores vs current | Complexity | Risk |
|---|---|---|---|---|
| A. Current `readFloatLE` + `Array.from` | 97 / 105 / 122 (you measured ~220 in-app) | — | status quo | allocates ~31MB transient per 5,000-row scan |
| **B. `Float32Array` view (+copy iff misaligned)** | **2.9** | **Object.is-identical, all 2,000** | ~5 lines, one function | host-endianness assumption (LE-only — always true on Windows) |
| C. Byte-wise `readFloatLE` dot, no decode | ~19 | identical, all 2,000 | ~7 lines, duplicates decode logic at both call sites | same endianness safety, slower |
| C2. Byte-wise `DataView.getFloat32` dot | 9.3 | identical, all 2,000 | ~7 lines | same |
| D. Decoded-vector cache (dot only = the floor) | 3.6 | identical | new Map, two-phase query, invalidation on `storeEmbedding`/delete | **not worth it — see below** |
| Bun/JSC (non-production engine) | A: ~14, B: ~6, all compressed | identical | — | JSC is not what Electron runs |

Equivalence proof: all options produced `Object.is`-identical scores on all 2,000 vectors (each element is the f64 rounding of a stored f32 — identical whether read via `readFloatLE`, `DataView`, or `Float32Array` load — and the dot product accumulates in f64 in the same order). Top-20 ordering identical. The misaligned-blob copy path in B verified correct against a deliberately offset `Uint8Array`.

**The decisive finding for option D:** a cache only eliminates the decode, and the view already makes the decode free. After fix B, the remaining ~3ms/1,000 *is* the dot product, which a cache still pays every keystroke. What a cache could additionally save is blob *materialization* — measured via `node:sqlite` (the actual driver: `@effect/sql-sqlite-node` wraps `DatabaseSync`, verified in `node_modules`): ~39ms to materialize 5,000 rows × 3KB blobs, vs ~28ms for a metadata-only scan. So the best a two-phase id/`created_at` diff + lazy blob fetch buys is ~11ms per keystroke on a 5,000-item library — nowhere near worth a `Map`, an extra query, and invalidation logic keyed on `item_embeddings.created_at`. Revisit only if libraries reach tens of thousands of items; at that point the ~28ms row-scan floor also needs attention (e.g., scoring in a worker thread or `sqlite-vec`).

## Recommended code

```ts
function decodeFloatVector(blob: Uint8Array | null, dimension: number) {
  if (!blob || blob.byteLength !== dimension * 4) return null;
  // Stored as little-endian float32; a view is valid because every host we ship
  // is little-endian. Copy only if a driver ever hands us an unaligned view.
  const aligned = blob.byteOffset % 4 === 0 ? blob : blob.slice();
  return new Float32Array(aligned.buffer, aligned.byteOffset, dimension);
}
```

Nothing else changes. `dotProduct` already takes `ArrayLike<number>`; the `vector.length !== queryVector.length` guards at both call sites still hold; `searchSimilar` gets the same speedup through the shared helper for free.

Pitfall checklist, verified rather than assumed:

- **Alignment:** `node:sqlite` returns a *fresh* `Uint8Array` per blob — I confirmed `byteOffset === 0` and `buffer.byteLength === blob.byteLength` on both full blobs and `substr()` slices under Node 26. `byteOffset % 4` will be 0 in practice; the `slice()` fallback costs 3 lines and covers any future driver returning views into shared buffers.
- **Endianness:** `readFloatLE`/`writeFloatLE` are endian-independent; a `Float32Array` view reads host-endian. Windows is always little-endian, so this is safe — but it's the one real semantic assumption, which is why the comment earns its place.
- **Buffer pool:** not applicable — `node:sqlite` doesn't pool; each row is a fresh allocation. Even if a driver pooled, the view is bounded by `byteOffset`/`byteLength` and is transient. One caveat worth remembering: *if* someone later caches these `Float32Array`s, views over pooled slabs would pin the whole slab — the copy-on-misalign path wouldn't protect against that.
- **Scores:** bit-for-bit identical, so result ordering cannot change.

## What I rejected, and what's fragile in the current code

- **Byte-wise dot (C/C2):** saves the decode allocation but keeps a per-element native call — 3–7× slower than the view under V8 (9.3–19 vs 2.9ms/1k), and it would fold decode+score into one function duplicated or reshaped at two call sites. Strictly worse than B on both axes.
- **Decoded-vector cache (D):** as shown, it's already at the same floor as B minus ~11ms of blob transfer per 5,000 rows. Two-phase queries plus invalidation on `storeEmbedding`'s `ON CONFLICT` update and cascade deletes is real machinery for nothing at alpha scale.
- **`sqlite-vec` / ANN index:** a new native dependency with Electron ABI packaging concerns to save a ~55ms/keystroke scan. Pure scope creep per "yagni".
- **What's actually fragile today:** the per-row `Buffer.from` wrapper + 768-element packed-double array is ~6.3KB of garbage per row — **~31MB of transient allocation per keystroke** on a 5,000-item library, which forces scavenges on the main thread. That GC pressure is likely why your in-app measurement (~220ms/1k) exceeds my synthetic decode number; fix B eliminates it entirely.
- **Post-fix bottleneck:** after B, the ~39ms SQL blob materialization becomes the dominant per-keystroke cost — worth knowing so nobody is surprised. Also note `embedQueryForSearch` runs ONNX inference per keystroke in `main.ts` (search.ts line 307) — likely comparable or larger than the entire post-fix scan; out of scope here, but the real "scan every vector every keystroke" cost is already bounded.

## Confidence

**High** on correctness and score equivalence (verified bit-for-bit, including the misaligned path) and on the cache-is-pointless conclusion (the math is structural, not measured). **Medium-high** on the absolute speedup in the real app: I benched Node 26's V8, not Electron 45's exact Node build, and real rows pass through Effect's row builder (which adds per-row cost to *both* current and fixed paths — it flatters neither). What I could not verify: Electron-runtime numbers, GC pause behavior in-app, and whether ~55ms/keystroke total at 5,000 items is the UX target you want — but it's ~20× better than today with 5 lines changed.
